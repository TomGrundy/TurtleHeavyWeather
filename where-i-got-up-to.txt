  2. Feasibility Verdict: Pure GitHub Pages + GitHub Actions vs. Home Server
  Yes, a pure GitHub Pages + GitHub Actions deployment is possible, with important architectural constraints (analyzed in turtleheavyweather/docs/hosting-feasibility.md):
  1. Spatial Mesh Instead of 15,000 Live Queries: You cannot query APIs per suburb across all ~15,000+ Australian suburbs or hold secret API keys in a browser WASM app. Instead, the
  Actions job collects data on a representative Australian BOM station / regional hub mesh (~100–250 nodes), and the browser maps any suburb, postcode, or GPS coordinate to its nearest
  node(s) and fetches a small sharded JSON file (nodes/{node_id}.json).
  2. Preventing Git History Bloat: Committing rolling forecasts/observations to main on every cron run will bloat .git toward GitHub's 1 GB soft / 5 GB hard limit. The workaround is
  storing the rolling 7-day SQLite weather.db on a force-pushed single-commit orphan branch (data-state) (or GitHub Release asset) and publishing the built WASM site + JSON shards via
  actions/deploy-pages.
  3. Cron Jitter & Limits: GitHub Actions schedule runs best-effort (often delayed 15–90+ minutes), auto-disables after 60 days without human commits, and only gives unlimited minutes
  on public repos (private repos have 2,000 mins/month). Also, commercial weather sites often block shared Azure/GitHub runner IPs.
  4. Home Server Path (Dual-Target Shared Core): Because thw-core, thw-sources, thw-store, and the Leptos frontend share the same contracts, THW-012 provides a clean Home Server path
  (thw-server Axum binary + SQLite WAL + Caddy/Tailscale/Docker/systemd) if you want strict sub-hourly syncs, residential-IP scraping, or on-demand caching.
